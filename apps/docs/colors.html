Colors

The color system: base tokens plus formulas. Every semantic token is derived from a handful of OKLCH numbers per family — no color ramps.

Model: bases + formulas

A palette is five base colors — Neutral (chroma, hue, page/raised/sunken lightness) and Accent / Success / Warning / Danger (lightness, chroma, hue). Formulas derive every semantic token from them: surfaces, text, borders, fills, on-* contrast poles, hover states and tints.

Fills use a polarity branch: a base lightness up to 0.70 produces a vivid fill with a white contrast pole, a lighter base produces a saturated pastel with a near-black pole — the branch jumps the APCA dead zone. The light theme fill maps to the darker step, the dark theme fill to the lighter one, mirroring the current palette.

Defaults are calibrated and APCA-validated in CI. Beyond the calibrated defaults the formulas make no guarantees — contrast is the host's responsibility, which is why the palette widget (the floating button in the corner, on every docs page) carries a live pass/fail table for self-checking.

Semantic tokens

Components consume only these names (theme notes). The swatches show the values currently in effect — open the palette widget to change them and watch this grid follow.

Surfaces

The gray page gamut — every neutral look of a component (badge without a variant, secondary/outline/ghost buttons, table rows, fields) is built from exactly these tokens, so it never follows a re-themed brand family. Dark-theme hover takes the full raised step: a half-step reads as invisible on the wide dark surface ramp.
